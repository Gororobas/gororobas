Gororobas authentication

A guided reading of the move from Better Auth to @yielded/auth. Start with the story, step through each login, then inspect the tables and follow a protected request into our policies.

1. A login is a chain of decisions

We first prove that this browser started the flow. Then we prove possession of a mailbox or an external identity. Then we decide which local account that proof belongs to. Only then do we issue a Gororobas session. On a protected request, a separate step loads the person's current roles and memberships.

Browser→Proof→Account→Session→Roles→Policy

Better Auth bundled much of this behind its router and opened its own DatabaseSync("gororobas.db") connection. Its magic-link delivery and social-provider credentials were placeholders in HEAD. The new implementation makes these decisions explicit as Effect services, operation handlers, and SQL transactions. Email delivery is implemented; OAuth protocol checking is delegated to openid-client.

The extra tables are mostly durable memory for that chain: “was this request already handled?”, “is this proof still current?”, “did we send it?”, “was it consumed?”, and “is this caller exceeding a limit?”. They are not seventeen different kinds of user.

A session carries { authSubjectId }, identity metadata, and authentication assurance. It does not carry platform roles or organization memberships. That is why authentication success alone does not grant permission to censor media or edit an organization.

2. The library supplies machinery; the app supplies meaning

Piece Its job in this worktree Read the implementation
AuthContract The shared wire agreement: payloads, result schemas, strategy names, credential slots, and HTTP actions. It describes what clients can call; it does not implement account creation.
Operations Server commands with typed handlers. Public HTTP fields are decoded and trusted cookies are injected before invoking them. Each handler decides what to persist and which credentials to issue or clear.
Proofs The mailbox challenge engine: issue, throttle, dispatch, verify, create a short-lived continuation, and consume it. It does not know our profiles or people tables.
Sessions / AuthenticationAuthority Check active subjects and credentials, compare security revisions, evaluate factor requirements, then establish and verify stateful sessions. A revision is a version stamp, not a password.
AuthPersistence Implements library persistence ports using our Effect SqlClient. Its descriptor generates a storage layout; our mapping names SQL columns and connects its generic subject to auth_subjects.
App-owned identity logic Creates a local account, public PERSON profile, NEWCOMER person, and credential. OAuth additionally decides whether to create, reuse, or explicitly link an external identity.
HTTP + Layer wiring Adapts operation results to cookies and routes, installs native session security, provides origin/binding configuration, delivery, SQL persistence, and provider protocol services.
Two Auth descriptors are intentional. AppAuth is the public service with our custom strategies. StorageAuth is a storage capability selector using Email.makeAddresses to enable proof persistence in the composed adapter. Its email-address management operations are never installed publicly. That selector explains the otherwise puzzling unpopulated email tables.

3. Follow one magic link

Alice enters a name and email. The page stores non-secret flow context in localStorage; the server stores browser credentials in HttpOnly cookies. Opening the emailed link in the same browser gives the page the token, but merely loading the page does not verify it or create an account.

The binding digest covers a version label, flow ID, verified browser verifier, normalized email, and name. Changing the name or email between request, verify, and complete changes the digest and fails the binding check. The name is signup input; an existing account's stored name is not overwritten.

Why verify and complete are separate

Verify spends the email token and issues a 30-second continuation credential. Complete spends that continuation, provisions the local account, and establishes a session. The continuation is a short-lived authorization to finish this exact action; it is not a logged-in session. Its secret is carried in an HttpOnly cookie while its public ID is in the JSON result.

4. OAuth proves an external identity, then we decide the account

These providers use OpenID Connect on top of OAuth. The authorization code is exchanged server-side, and openid-client validates the signed ID token, issuer, nonce, and protocol response. The local identity key is (provider, issuer, subject). Email is only a signup prerequisite, never permission to silently connect accounts.

State, nonce, PKCE, and browser binding do different jobs

State looks up the exact pending OAuth flow. Nonce connects the validated ID token to that authorization request. PKCE requires the server's verifier to redeem a Google/Microsoft code. Request binding requires the browser that began the Gororobas flow to finish it. Apple uses a POST callback and no PKCE here because it does not advertise support.

Why the callback only redirects

Apple posts from another site; the originating browser's SameSite cookies may be unavailable on that cross-site POST. The relay takes code/state and redirects them into a first-party URL fragment. It does not spend state, exchange the code, or log anyone in. Confirmation then POSTs to completeOAuth with the originating binding cookie, trusted Origin, and CSRF header. Google/Microsoft GET callbacks use the same relay pattern.

Microsoft and account linking

The adapter only treats explicit email_verified === true or "true" as verified. An unverified provider mailbox cannot create a new account. The intended Microsoft path is magic-link signup, then explicitly connect Microsoft while freshly authenticated. Once the identity is linked, later sign-ins resolve the stable provider subject and do not require a fresh verified email claim. This rule is enforced from the validated claims, not just the provider's name.

5. Every authentication table, with a reason to exist

auth_subjects and the two OAuth tables are app-owned. The remaining fourteen are selected/generated by the Yielded adapter. Each table is shown below, including the three that current flows do not populate. Most proof rows have no account foreign key because signup proof must work before an account exists.

module_id separates proof/email modules; purpose separates actions such as magic-link sign-in. version supports conditional updates under races. A digest is a token verifier; the raw token is not kept in these durable proof/session records. retention_until retains replay/abuse history beyond the user-visible expiry.

6. Operations describe contracts; storage enforces one-use behavior

access: "any" allows a guest to enter a login flow. exposure: "public" exposes an operation through the contract. credentials: true allows credential commands, such as Issue/Clear, to reach the HTTP cookie adapter. None of those labels removes browser admission checks.

Action Replay intent Credential effect Actual enforcement
beginMagicLink Non-idempotent Issue request-binding Signed binding tied to flow, generation, and expiry
requestMagicLink Idempotent Read binding Request ID + fingerprint; replay receipt, suppress duplicate dispatch
verifyMagicLink Single-use Read binding; issue continuation Conditional proof transition + command journal + failure budgets
completeMagicLink Single-use Read binding/continuation; issue session; clear both Continuation consumption + session flow deduplication
beginOAuth Non-idempotent Issue request-binding Unique flow ID/state; bound pending row with expiry
completeOAuth Single-use Read binding; issue session; clear binding DELETE ... RETURNING exact unexpired flow + session deduplication
getSession / signOut Library session actions Read or revoke/clear session Stateful session verification and revocation

The contract's requestFields maps cookie slots into the server-only input. The browser never supplies its request-binding or continuation secret as an ordinary JSON payload. Handler output has { value, credentialCommands }; only the public value becomes action JSON, while commands become credential transport changes.

The browser page sends { payload: ... } to camelCase action paths, such as /api/auth/verifyMagicLink. Responses use a Success envelope. Under HTTPS, cookies use Secure, HttpOnly, SameSite, and the __Host- naming rules. The session cookie is __Host-gororobas-session.

Authentication mutations require a trusted Origin, the x-effect-auth-csrf: 1 header, and JSON content type. The OAuth relay routes are deliberately separate from those completion mutations. CORS configuration alone is not the authentication admission check.

7. What changes for our policies' runtime

The application ManagedRuntime still owns shared SQL, cluster, and reporting services. Authentication layers and API handlers use that SQL service. Both entry points provide server-wide IdGen and environment-selected email delivery through ServerServicesLive; authentication now requires those services from its host. The old Better Auth service/router bridge and its separate database connection are gone. Yielded middleware supplies request-local authentication; it does not require running policy effects in a separate runtime.

For a protected media upload, native session security validates the cookie and provides AuthenticationHttp.CurrentSession. The handler provides SessionServiceLive to its effect. That layer reads the verified subject ID, loads people.access_level and organization_memberships, and provides our SessionContext. Existing policy combinators read that context and use the existing permission map.

Cookie→CurrentSession→SessionServiceLive→SessionContext→Policies
Try a protected media upload

Roles are loaded when this handler's layer is provided, so a later request sees changed roles/memberships without rewriting the session token. Within one resolution, policies use that loaded snapshot. A missing person now fails with UnauthorizedError; this resolver no longer turns absent authentication into a VISITOR session. Protected endpoint middleware rejects absent authentication before role resolution. Public handlers do not automatically acquire a visitor context from this layer.

Fresh login evidence and session lifetime are different clocks. The one-possession-factor requirement permits evidence at most five minutes old when establishing authentication. Sessions may then last up to thirty days, with seven-day idle expiry and library renewal. OAuth linking separately checks authenticatedAt within five minutes at both begin and completion; renewing a session is not a new login.

Invalidation has layers. Setting subject active=false or changing its security_revision invalidates stateful session verification. Disabling a credential rejects future login using that credential. The current stateful verify implementation checks subject status/revision, not every credential's active flag on every request. To invalidate already-issued sessions for a compromised credential, use subject/session invalidation as well.

8. “Prepare” does not mean everything shares one transaction

Yielded uses prepared commit receipts to keep public results and credential issuance tied to successful persistence. Reading a prepared result before its transaction owner commits is forbidden. Our handlers use readProofCommit and session commit.read to retrieve committed results.

Boundary What commits together What a later failure means
Magic-link request Proof issuance decision, fingerprint/replay receipt, proof generation, abuse accounting Scheduling happens afterward. A committed receipt is not a guarantee that an email arrived.
Magic-link verify One-use token decision and continuation creation The original link cannot simply be replayed if completion later fails.
Magic-link complete Continuation consumption is its own proof commit Provisioning failure burns the continuation. Start a fresh link.
Account provisioning Subject + profile + person + strategy credential/identity writes Partial signup rolls back. A later session failure can leave a fully provisioned account without a session.
OAuth complete One DELETE atomically claims the exact bound flow Provider exchange happens after claim. Exchange/provisioning failure burns the OAuth flow.
Session establishment Current authority/factor checks, authentication-flow replay marker, and stateful session record Cookie commands are returned only after committed session creation.

This implementation chooses one-use safety and simple transaction ownership over resumable whole-login transactions. It is explicitly documented in the magic-link and OAuth handlers. Nothing here is a cross-database transaction with an email or identity provider.

9. The practical limits of this implementation

Clocks and budgets

Browser binding and OAuth flow: at most 10 minutes. Email proof: 5 minutes. Continuation: 30 seconds. Default proof policy: 5 failed attempts maximum, 30-second resend cooldown, 1 delivery attempt, and 1-hour request retention. Our Identifier-bound proofs charge identifier and global action windows. The policy also defines subject windows for subject-bound proof types; those are not charged for our anonymous Identifier binding. Host ingress adds a default network token bucket with capacity 20, refilling over an hour.

Email delivery is queued in this process

The default scheduler has one scoped worker and 64 pending tasks, with a 10-second task budget. Durable generation rows track delivery decisions, but plaintext dispatch work lives in a private in-memory closure. This is not a restart-safe email outbox. Process shutdown can lose pending delivery work. Delivery errors distinguish definitely not accepted from acceptance unknown so uncertainty is not casually retried into duplicate messages.

Network limiting and reverse proxies

By default the HTTP adapter derives networkKey from the transport remoteAddress, or uses a supplied trusted ProofRequestContext. It does not trust an arbitrary client-supplied IP field. Behind Caddy, inspect whether the remote address is the proxy's address: otherwise different users can share one bucket. The fallback RateLimiterStore is process-local; multiple server processes do not share its counters. Durable proof budgets are a separate defense.

Browser experience is intentionally narrow

The login page is a development/first-party confirmation UI. It stores one magic-link context and one OAuth context per origin, while binding credentials use fixed cookie slots. Starting parallel login attempts can overwrite earlier context. Magic links require the originating browser, rather than signing in any browser that holds the URL. The page offers provider buttons for linking immediately after login; there is no full account-management/unlinking UI here.

Schema setup and the subject-reference rename

The Better Auth move resets SQL/Effect migrations to a regenerated initial schema; it does not upgrade a Better Auth database/session cookie in place. An incremental migration now upgrades that initial Yielded schema to auth_subject_id/link_auth_subject_id and rewrites the old accountId claim in stored session records. It preserves populated subject references and already-renamed claims. Historical initial migrations deliberately retain their original names.

Configuration and what tests establish

AuthenticationLive requires AUTH_BINDING_KEY and uses AUTH_ORIGIN (default https://localhost:4443). Development/test selects Mailpit; production selects Resend. Each OAuth provider requires both ID and secret or neither. Configured clients perform discovery during layer construction; partial configuration or discovery failure can prevent that layer from starting. The tests cover HTTP flow binding/replay, account creation/linking, expiry, revocation, provisioning rollback, and locally signed protocol responses. They do not establish that live provider credentials or a production reverse proxy are configured correctly.

What changed during this walkthrough

Renamed yielded-auth.ts to magic-link.ts and exported magicLinkStrategy, matching the OAuth strategy module. Moved combined AppAuth and HTTP factory into app-auth.ts, so a magic-link file no longer owns OAuth composition. Updated consumers. Renamed shared insert helpers to insertAuthSubject, insertPersonProfile, and insertPerson, since both strategies use them. These are organizational improvements; authentication behavior and schema are preserved.

The follow-up renamed application references to authSubjectId/auth_subject_id, separated OAuth SQL queries/mutations from provisioning, and centralized email/ID services. Signup now creates NEWCOMER people, matching people.feature. Schema-based property tests cover signup order/linking, rollback, flow consumption, and migration preservation. The ID claim remains redundant with session.subjectId; policy roles and memberships continue to come from SQL.

Vocabulary without the reference-manual voice

Subject
The local account whose identity a session represents.
Credential
An independently active/revisioned way to authenticate that subject. Magic-link credential ID is the account ID; OAuth gets its own oauth: ID.
Assurance / evidence
What proved authentication, when, and with which factors. Here both methods count as possession; neither claims user verification or phishing resistance.
Continuation
A short-lived one-use permission to finish a verified proof action.
Request binding
A signed browser credential tying a flow to its initiating browser.
Security revision
A stored version stamp. Sessions/evidence captured under an older version can be rejected after it changes.
Layer
A recipe for acquiring and providing Effect services, with lifecycle and dependency management. Shared layer identities can be memoized within a build; providing the role layer inside a handler makes role resolution part of that request.
