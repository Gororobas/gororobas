## One contract, server to client

Describe your session claims and the actions clients may call with Effect Schema.
The server, HTTP routes, and client share that definition.

<CallSites
  sites={[
    { label: "Server handler", code: "yield* auth.signIn({ email, password })" },
    { label: "HTTP route", code: "POST /auth/signIn" },
    { label: "Client Effect", code: "yield* client.auth.signIn({ email, password })" },
    { label: "React", code: "const [result, signIn] = useAtom(auth.signIn)" },
  ]}
>
  <Snippet src="../README.md" region="auth-contract" />
</CallSites>

Inputs and public results use the same schemas. Expected failures stay typed;
credentials travel through the private HTTP boundary. Clients reach only the
actions you declare.

## An ordinary Effect service

Choose your methods and session behavior, then supply their dependencies with
Layers. Inside a handler, `yield* AppAuth` gives you auth alongside your other
application services.

<Snippet src="../README.md" region="auth-server" />

Provide storage, account policy, hashing, and keys to `AuthRoutes`; its Layer type
shows what is still needed. Your app owns account creation and authorization.
[See how Auth fits into Effect](/auth/guide/effect/), or
[add it to an existing HttpApi](/auth/guide/http-and-client/#join-an-existing-httpapi).

## Effect on the client too

Derive an Effect HttpClient service and atoms from the shared contract:

<Snippet src="../README.md" region="auth-client" />

Read `auth.session` and dispatch `auth.signIn` or `auth.signOut` with ordinary
`@effect/atom-react` hooks. Auth mutations refresh auth queries automatically.
Compose workflows in Effect and connect your application's queries through
reactivity keys. [Build the client](/auth/guide/client/).

## Your accounts, your storage

Keep your customer or employee model. Use managed auth tables, map your own SQL
schema, or supply storage services for a different backend. Changing storage
Layers keeps the contract and client intact.

<StorageLadder />

The [database and backend guide](/auth/guide/storage/) explains the choices and
the durability each implementation must provide. Four
[runnable account apps](/auth/guide/examples/#run-an-account-app) show the same
workflows across Drizzle, Effect SQL, and a non-SQL store.
